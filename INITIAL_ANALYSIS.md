# LShift: начальный анализ

Дата: 21 октября 2026, Europe/Moscow.
Исторический документ: первоначальное исследование и предложение архитектуры. После анализа начата реализация MVP; актуальное состояние см. в [README](README.md) и [проверках](docs/VALIDATION.md). Игровые замеры пока не проводились.

Продолжение: [исследование существующих решений](OPEN_SOURCE_REVIEW.md) от 21 октября 2026, Europe/Moscow. Загружены и изучены через SocratiCode четыре open-source проекта и один сравнительный публичный проект с UI Automation и неустановленной лицензией. Анализ поддерживает предложенное разделение наблюдателя и текстовых адаптеров, но не подтверждает универсальный доступ к полям или отсутствие игровых задержек. Выбор стека остаётся предложением.

## Цель и подтверждённые требования

- Два коротких нажатия левого Shift исправляют раскладку последнего слова; при наличии выделения обрабатывается выделенный текст.
- Этот же жест переключает язык ввода. Действие относится к текстовому полю.
- Программа продолжает работать параллельно с играми. Распознавание игр и отключение по списку процессов не должны быть основой решения.
- Главный приоритет — корректный способ работы с текстовыми полями вообще. Discord и Telegram — примеры для проверки, а не граница поддержки.
- Требуется максимально нативная реализация для Windows с минимальным вмешательством во ввод.

Сообщённые пользователем задержки Caramba — основание требований. Их конкретная причина не диагностирована: наличие клавиатурного хука, блокирующих вызовов или другой причины в установленной версии не проверялось.

| --- | --- | --- |

| Rust и Windows bindings | Нативный код и более строгая безопасность памяти; COM и Win32 потребуют interop и участков unsafe. | Полноценная альтернатива, если предпочесть Rust |
| C# и .NET с Win32 interop | Быстрее разработка интерфейса и логики; больше инфраструктуры исполнения. Асинхронная архитектура возможна и здесь. | Допустимо; оснований считать C# причиной игровых задержек нет |

Выбор C++ — инженерная рекомендация для маленькой системной утилиты, а не доказательство большей плавности игр. Критичнее отсутствие нашей программы на синхронном пути доставки каждой клавиши.

Первое исполнение: обычное приложение пользователя x64, скрытое служебное окно, стандартный трей Windows. Драйвер, служба, собственная DLL в чужих процессах и права администратора для базового сценария не нужны. Диалоги настроек можно сделать на Win32, когда подтвердится механизм ввода.

## Основа: асинхронное наблюдение

`WH_KEYBOARD_LL` вызывается перед помещением события в очередь потока и требует быстрого возврата. Microsoft рекомендует рассмотреть Raw Input для асинхронного наблюдения за клавиатурой. Поэтому глобальный низкоуровневый хук не предлагается для первого варианта. Это свойство API, а не установленный диагноз Caramba. [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc).

Клавиатура регистрируется через Raw Input с `RIDEV_INPUTSINK` на служебное окно. Это позволяет получать события в фоне. Регистрация выполняется в нашем процессе, без перерегистрации устройств игры. `RIDEV_EXINPUTSINK` не подходит как равнозначная замена: при регистрации foreground-приложения на Raw Input фоновый получатель может перестать получать события. [RAWINPUTDEVICE](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawinputdevice).

Это устраняет зависимость доставки клавиши от возврата нашего hook callback. Оно не означает нулевую нагрузку на CPU и не является обещанием отсутствия любых задержек на любой машине.

Raw Input подписывает нас на события клавиатуры, а не исключительно на левый Shift. В обработчике остаются только разбор короткого события, состояние нажатых клавиш и автомат жеста. Не выполняются чтение текста, UI Automation, файловый ввод-вывод, сетевые запросы или ожидание рабочего потока. Не нужен постоянный опрос клавиатуры таймером.

## Текст запрашивается по команде

Предлагаемый поток работы:

1. Обработчик Raw Input распознаёт два законченных коротких нажатия левого Shift.
2. Короткий запрос передаётся отдельному рабочему потоку; очередь ограничена, старые команды не накапливаются.
3. Рабочий поток проверяет foreground-окно и сфокусированный элемент через нативный UI Automation.
4. До чтения содержимого проверяются доступность, фокус, парольный режим и признаки редактируемости. Само наличие TextPattern не доказывает редактируемость: его предоставляют и документы для чтения.
5. При наличии одного непустого выделения запрашивается ограниченный объём выделенного текста. Иначе запрашивается диапазон рядом с активным курсором и определяется слово перед ним.
6. При неподдерживаемом поле, неизвестном состоянии, изменившемся фокусе или слишком большом диапазоне команда прекращается до изменения текста.
7. После преобразования выполняется проверенный для данного типа поля способ замены и запрос нужной раскладки. Фактический результат проверяется отдельно от успешного вызова API.

В обычном наборе программа не реконструирует строку по клавишам и не хранит историю текста. Нужный текст читается непосредственно из поля только по жесту. Это также уменьшает зависимость от вставки текста, автокоррекции и перемещения курсора, которые делают буфер нажатий ненадёжным.

`TextPattern2::GetCaretRange` предоставляет диапазон активного курсора, если провайдер приложения поддерживает этот интерфейс. Это возможность API, а не подтверждённая поддержка в Discord или Telegram. [GetCaretRange](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomationtextpattern2-getcaretrange).

UI Automation используется в отдельном COM MTA потоке без окон. Поток Raw Input никогда его не ждёт. У UI Automation есть настройки таймаутов соединения и запросов; дополнительно ограничивается срок актуальности нашей команды. Таймаут запроса не следует считать универсальной гарантией безопасного прерывания любого зависшего провайдера. [Threading Issues](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-threading), [IUIAutomation2](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nn-uiautomationclient-iuiautomation2).

## Главная неопределённость: изменение текста

UI Automation TextPattern позволяет читать диапазоны и управлять выделением, но не содержит универсальной команды замены текста диапазона. Вызовы могут обращаться к другому процессу и иметь заметную стоимость. Поэтому нельзя переносить их в обработчик каждого нажатия. [Text and TextRange](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-about-text-and-textrange-patterns).

Имя TextEditPattern не решает задачу автоматически: соответствующий интерфейс добавляет получение активной композиции и диапазона конвертации, а не универсальный ReplaceText. [ITextEditProvider](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationcore/nn-uiautomationcore-itexteditprovider).

Варианты, которые нужно сравнить в исследовательском прототипе:

- Адресное редактирование стандартного контрола через его нативный API. Предпочтительно там, где это сохраняет undo, курсор и форматирование; не покрывает все произвольные поля.
- Выделение диапазона через UI Automation и ввод преобразованного Unicode через `SendInput`. Потенциально шире покрытие; необходимо проверить реальное поведение приложений, undo, форматирование, обработку Unicode и гонки фокуса.
- Text Services Framework, если внешнего доступа окажется недостаточно. TSF предназначен для служб текстового ввода, но требует регистрации COM in-process сервера и языковых профилей, усложняя развёртывание и взаимодействие с приложениями. Это отдельный архитектурный вариант, а не бесплатное расширение фоновой утилиты. [Text Service Registration](https://learn.microsoft.com/en-us/windows/win32/tsf/text-service-registration).

`ValuePattern.SetValue` не следует использовать как универсальный способ переписать всё содержимое поля ради одного слова: это другой масштаб изменения с риском для undo, позиции курсора и форматирования.

`SendInput` зависит от текущего фокуса и состояния клавиш; UIPI ограничивает ввод в процессы более высокого уровня целостности. Повторная проверка фокуса уменьшает риск, но не делает получение диапазона и синтетический ввод атомарной операцией. Успешное число отправленных событий не доказывает, что редактор принял правильный текст. [SendInput](https://learn.microsoft.com/windows/win32/api/winuser/nf-winuser-sendinput).

Предложение: сначала исследовать чтение и распознавание без записи; включать изменение только после проверки всего сценария. Буфер обмена и последовательности «скопировать, стереть, вставить» не предлагаются как скрытый универсальный fallback.

## Требование «любой текстовый инпут»

Это остаётся целью пользователя. Оно не считается заменённым требованием «работать только в нескольких популярных приложениях».

Однако приложение может реализовать поле собственным рендерингом и не предоставить внешний доступ к содержимому, курсору или признакам редактирования. Тогда определить его смысл и исправить слово универсальным внешним Win32 API невозможно. TSF также требует сотрудничества приложения и не делает любое нарисованное поле автоматически доступным.

Практически проверяемая стратегия — опираться на стандартные возможности поля, а не на имя процесса. Неизвестное поле нельзя считать разрешённым для удаления или ввода текста. Если полного покрытия этими API недостаточно, потребуется отдельно выбрать между дополнительными интеграциями и более узкой поддержкой; такое сокращение требований пока не согласовано.

Игровой чат при наличии корректного текстового интерфейса потенциально обрабатывается по тем же правилам. Поведение конкретного античита и собственных полей игры остаётся предметом проверки. Асинхронность наблюдателя сама по себе не подтверждает совместимость античита.

## Правила жеста и языка — предложено, кроме подтверждённого объёма текста

- Учитывается физический левый Shift, включая отпускание; автоповтор не считается вторым нажатием.
- Начальный интервал между нажатиями — около 350 мс, длительность отдельного короткого нажатия — до 250 мс. Это параметры для проверки удобства, не окончательная спецификация.
- Удержание другой клавиши, сочетание с Ctrl/Alt/Win, смена foreground-окна и потеря достоверного состояния отменяют распознавание. Пример обязательной проверки: удержание W и нажатия Shift не создают команду.
- Внешние нажатия Shift не подавляются. Приложение продолжает их видеть; возможны конфликты с его собственным двойным Shift. Устранение любого такого конфликта требует вмешательства в доставку событий и меняет исходный компромисс.
- Системное залипание клавиш и его сочетания проверяются; настройки Windows самовольно не меняются.
- Начальная пара раскладок предлагается как стандартные Russian ЙЦУКЕН и English US QWERTY. Поддержка других раскладок не считается отклонённой.
- Преобразование идёт по клавишам выбранной пары, с сохранением регистра, а не по правилам перевода или транслитерации.
- Для обычного сценария «ghbdtn» становится «привет», дальнейший ввод идёт в русской раскладке; обратное исправление должно работать симметрично.
- При отсутствии слова в подтверждённом редактируемом поле предлагается только переключать язык. Вне такого поля предлагается ничего не менять.
- Границы слова возле пробелов и пунктуации, смешанные алфавиты, несоответствие текста текущей раскладке и длинное выделение требуют явных правил перед реализацией. Неоднозначный текст нельзя исправлять эвристически без обсуждения.

Переключение раскладки адресуется фокусу целевого приложения через системный запрос; `ActivateKeyboardLayout` только в нашем потоке не решает задачу чужого приложения. Приложение вправе отклонить `WM_INPUTLANGCHANGEREQUEST`, поэтому после запроса нужно проверить фактическую раскладку. Редактирование текста и смена языка не образуют единую транзакцию; частичный результат необходимо различать. [WM_INPUTLANGCHANGEREQUEST](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-inputlangchangerequest).

## Последовательность прототипирования

1. **Наблюдение и жест.** Минимальный Win32 процесс с Raw Input, без чтения и изменения текста. Проверить левый/правый Shift, удержание, сочетания, частый ввод, отмену и отсутствие накопления команд.
2. **Доступ к полю.** Проверять фокус и получать ограниченный диапазон только по жесту, без записи. Матрица: стандартное поле Windows, браузерные input/textarea/contenteditable, Discord и Telegram. Их фактический backend и качество accessibility заранее не предполагаются. Негативные случаи: пароль, read-only, canvas, фокус вне редактора, зависший провайдер.
3. **Замена и раскладка.** Сравнить адресный API контрола и UI Automation с синтетическим вводом. Подтвердить результат глазами в приложении, undo, выделение, курсор, регистр, переключение языка и отмену при смене фокуса. Только сборка или возврат API недостаточны.
4. **Совместная работа с играми.** При одинаковой сцене и настройках сравнить выключенную утилиту, наблюдатель и полный прототип. Сопоставить время кадров, выбросы около нажатий, CPU и пробуждения; отдельно проверить двойной Shift в игре. Повторять прогоны, чтобы отличить эффект от естественного разброса. Тест, требующий действий пользователя, запускать после явного уведомления и готовности пользователя.

Для чистой проверки параллельно не должен работать другой переключатель с тем же жестом; изменение его состояния сначала согласовывается. Наблюдатель в тестовом режиме не пишет набранный текст и названия документов в диагностику. Допустимы счётчики, длительности и причины отказа.

Для автомата жеста и правил конвертации при реализации применять TDD. До сборок направить поддерживаемые кэши и build directory в проектную `.cache`, исключить её и `.tgrep` из Git. Сейчас зависимости не устанавливались, сборки и тесты не запускались.

## Текущее состояние и точка продолжения

Проверено: рабочая папка изначально пустая, Git-репозитория нет; архитектура существующего кода не исследовалась и не индексировалась. В Pet Hub не найдено проекта или расположения по LShift; регистрацию и записи журнала не создавали. На машине AMD64, сборка Windows 28000.3231; это наблюдение среды, не согласованная минимальная версия продукта.

Получено: исследование официальных API и рекомендация стека. Пользователь подтвердил объём исправления и общий приоритет совместимости. Выбор C++/Raw Input/UI Automation, параметры жеста и границы первой версии пока имеют статус предложения.

Следующий рекомендуемый шаг — исследовательский прототип этапов 1–2. Он должен проверить два независимых основания архитектуры: отсутствие блокирующей связи с доставкой клавиш и доступность правильного текста по команде. Изменение текста следует проектировать по его результатам. Неподтверждённые обещания универсального покрытия и отсутствия игровых задержек не считаются результатом анализа.
