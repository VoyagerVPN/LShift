# LShift: исследование существующих решений

Дата проверки: 21 октября 2026, Europe/Moscow. Это статический анализ сторонних исходников и рекомендация для проектирования. Исследуемые сторонние приложения не запускались, их сборки и игровые замеры не выполнялись. Причина задержек установленной Caramba этим исследованием не установлена. Последующая реализация собственного MVP описана в [README](README.md); её проверки отделены от результатов этого исследования.

## Результат

Маленькую утилиту для изменения раскладки написать возможно: рассматриваемые проекты содержат готовые примеры жестов, смены языка, конвертации и трея. Однако их внутреннее устройство существенно различается, а внешняя простота не доказывает отсутствие влияния на ввод.

Четыре основных проекта и дополнительный UIA-компаратор не дали готовой проверенной комбинации требований LShift: строго левый двойной Shift, исправление актуального слова/выделения только в редактируемом поле, асинхронное наблюдение без зависимости доставки клавиши от нашего callback и подтверждённая совместимость с играми. Это вывод об изученных версиях, не доказательство отсутствия любого подходящего проекта.

Рекомендация — собственное небольшое ядро на C++20/Win32. Открытые проекты использовать как источники отдельных решений и проверочных сценариев. Выбор стека и архитектуры остаётся предложением, а не утверждённой пользователем спецификацией.

## Сравнение механизмов

| Проект | Что выполняется при обычном вводе | Как исправляется текст | Что важно для LShift |
| --- | --- | --- | --- |
| dotSwitcher | Глобальный keyboard/mouse hook, накопление списка клавиш | Backspace и повторный ввод; выделение через clipboard | Исправление и Sleep идут синхронно из callback; проверки редактируемого поля на этом пути нет |
| MahouSwitcher | Hooks, буфер виртуальных клавиш; configuration API на части обычных событий | Смена языка, удаление и повтор клавиш; выделение через clipboard | `Task.RunSynchronously` не выводит обработку из callback; часть операций содержит ожидания |
| Cwitcher | Hooks, определение window/focus/caret и перевод клавиши в символ, tracker слова | Отдельный worker: Backspace/Unicode либо clipboard | Тяжёлая операция отделена, но текст всё ещё восстанавливается по нажатиям без строгого определения поля |
| kbsw | Короткий FSM двойных модификаторов в отдельном hook-потоке | Выделение через clipboard и таймерный автомат | Хороший пример FSM и очереди команд; последнего слова и разрешения по text-context нет |
| EN-UA_Switcher | Keyboard hook и буферы в автонаблюдателе; при разделителях Auto может синхронно обращаться к UIA | Native Edit API, UIA через SetValue всего поля либо SendInput fallback | Полезно разделение адаптеров, но оно не обеспечивает точную замену диапазона и строгий отказ для неизвестного поля |

### dotSwitcher: простой интерфейс, блокирующая команда

`KeyboardEventHook` → событие → `ProcessKeyPress` → `ConvertLast` исполняется синхронно. В `ConvertLast` после удаления стоят `Thread.Sleep(settings.SwitchDelay)`, синтетический Alt+Shift и повторный ввод. По умолчанию задержка 20 мс, README предлагает увеличение до 200 мс для одного сценария. Это ожидание в ветке исправления, а не на каждом обычном keydown. [Исходник](https://github.com/kurumpa/dotSwitcher/blob/199bf7270e47137d0a306667eba441b73f8ca871/Switcher/Switcher.cs#L241-L254).

Выделение читается Ctrl+C, при этом `BackupClipboard`/`RestoreClipboard` содержат только закомментированный код. Нет проверки, что Copy действительно заменил clipboard. Имена методов создают более благополучное впечатление, чем фактическая реализация. [Пустые методы](https://github.com/kurumpa/dotSwitcher/blob/199bf7270e47137d0a306667eba441b73f8ca871/WinApi/LowLevelAdapter.cs#L234-L264).

### Mahou: Task не означает асинхронность

Из keyboard callback вызывается `Task.RunSynchronously` для выделения и слова. В достижимых ветвях смены языка и clipboard присутствуют Sleep; на обычных keyup вызываются проверка конфигурационного файла и profile API. Физическое чтение диска на каждую клавишу не доказано. [Callback](https://github.com/kirvlasov/MahouSwitcher/blob/c706143b2040fa7a025efd4a379b1e5c6572ea6c/Mahou/Classes/KMHook.cs#L136-L177).

Последнее слово хранится как история виртуальных клавиш. Левый и правый Shift нормализуются в общий код, поэтому механизм двойных горячих клавиш не является готовой реализацией строго левого Shift. Clipboard backup ограничен тремя текстовыми форматами. Нельзя переносить эти выводы на недоступную текущую версию upstream Mahou.

### Cwitcher: полезное разделение, сохраняющее tracker

Callback ставит `WMAPP_TRANSFORM`, обработчик создаёт worker и запрещает вторую параллельную конвертацию. Ожидания clipboard и замены находятся на worker. [Callback/очередь](https://github.com/Astrent-bear/Cwitcher/blob/15d2f13eff634c2f1cda41d3485d4d465ffd37e7/src/input.c#L282-L375), [запуск потока](https://github.com/Astrent-bear/Cwitcher/blob/15d2f13eff634c2f1cda41d3485d4d465ffd37e7/src/ui.c#L2916-L2929).

Однако обычные нажатия всё ещё проходят через tracker и `ToUnicodeEx`. Удаление слова выполняется по сохранённой длине: цикл Backspace запрашивает 6+4 мс пауз на символ. Это задержка операции на worker, а не доказанная блокировка hook. Полезны ограничения параллельности и защита clipboard marker/sequence; tracker нельзя считать универсальным чтением поля. В комбинированном режиме слово имеет приоритет над выделением, что отличается от согласованного поведения LShift.

### kbsw: удачный пример автомата жеста

Четыре перехода down/up/down/up, timestamps события, отмена по постороннему событию, отдельный hook thread и `PostMessage` в основной поток — подходящие принципы распознавания. Clipboard обрабатывается таймерами; паузы 100–300 мс не выполняются в keyboard callback. [FSM и поток](https://github.com/tay64/kbsw/blob/d9401780ab6212f11f66217b03dcb9c96cf8dfc9/src/kbswhook.c#L9-L206).

Жест выбирает заранее привязанный HKL; последнее слово не реализовано. Fullscreen guard проверяется только при команде и не снимает hook — это не решение требования работать параллельно с игрой без зависимости от её определения. В конвертере найден статический выход за границы `keystate[256]` через индекс `0x400`, а маска режима `ToUnicodeEx` не соответствует названию. Последствия не воспроизводились. [Конвертер](https://github.com/tay64/kbsw/blob/d9401780ab6212f11f66217b03dcb9c96cf8dfc9/src/mojibake.c#L186-L210), [значения флагов Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-tounicodeex).

### UIA-компаратор: правильное имя API не гарантирует правильную операцию

EN-UA_Switcher добавлен для проверки подхода с UI Automation. Это публично доступный код с неустановленной лицензией, поэтому он рассматривается как сравнительный материал, а не как донор модулей.

В ручном режиме команды получает отдельный STA-поток GlobalHotkeyManager. В AutoMode, напротив, callback клавиатуры синхронно сообщает о границе слова, после чего `CaptureWordSnapshot` вызывает выбор адаптера, чтение текущего слова и предложения. Это выполняется до позднейшего `Task.Run` для части сценариев записи. Следовательно, наличие фонового Task в конце не означает, что все межпроцессные запросы уже вынесены из hook. [Чтение контекста](https://github.com/stokrattt/EN-UA_Switcher/blob/c69cb09534860687729e89d3ab3b49b09bf95006/src/Switcher.Engine/AutoModeHandler.cs#L326-L352).

UIAutomationTargetAdapter заменяет слово через `ValuePattern.SetValue(newValue)`, переписывая всё поле. Для выделения offset ищется через `fullValue.LastIndexOf(selectedText)`, а курсор восстанавливается синтетической навигацией. Это не адресная операция над полученным TextRange; повторяющийся текст создаёт статический риск выбора другого вхождения. Undo, форматирование и поведение приложения требуют отдельных проверок. [Запись слова](https://github.com/stokrattt/EN-UA_Switcher/blob/c69cb09534860687729e89d3ab3b49b09bf95006/src/Switcher.Infrastructure/UIAutomationTargetAdapter.cs#L180-L207), [выделение](https://github.com/stokrattt/EN-UA_Switcher/blob/c69cb09534860687729e89d3ab3b49b09bf95006/src/Switcher.Infrastructure/UIAutomationTargetAdapter.cs#L228-L273).

Полезна идея отдельных NativeEdit/UIA/SendInput адаптеров, но заявленная поддержка должна соответствовать гарантированным возможностям. У SendInputAdapter `CanHandle` безусловно возвращает Full; это нельзя переносить как подтверждение редактируемости неизвестного окна. [Fallback](https://github.com/stokrattt/EN-UA_Switcher/blob/c69cb09534860687729e89d3ab3b49b09bf95006/src/Switcher.Engine/SendInputAdapter.cs#L60-L65).

Это проверено и для полного ручного SafeMode-пути: после получения context и проверки исключения по имени процесса Coordinator ставит все Full-кандидаты перед ReadOnly. Поэтому UIA ReadOnly не является запретом последующего синтетического ввода. Это разрешение попытки в конкретном пути, а не доказательство успешной записи в защищённое поле. Полезные guards AutoMode — возраст snapshot, HWND/ProcessId и пользовательская активность — не следует автоматически приписывать ручному режиму.

NativeEditTargetAdapter действительно использует адресную замену EM_SETSEL/EM_REPLACESEL, однако читает текст синхронными SendMessage без прикладного timeout. UIA-адаптер заново получает FocusedElement без привязки к сохранённой identity. Отложенный fallback смены языка проверяет HKL старого потока, но затем может послать глобальное сочетание без новой проверки foreground. Эти различия должны быть учтены в собственных адаптерах. [Native edit](https://github.com/stokrattt/EN-UA_Switcher/blob/c69cb09534860687729e89d3ab3b49b09bf95006/src/Switcher.Infrastructure/NativeEditTargetAdapter.cs#L85-L137), [layout fallback](https://github.com/stokrattt/EN-UA_Switcher/blob/c69cb09534860687729e89d3ab3b49b09bf95006/src/Switcher.Infrastructure/NativeMethods.cs#L140-L180).

README и compatibility-документы сообщают об ограничениях конкретных Chrome-полей. Это сведения авторов, которые мы не воспроизводили. По коду подтверждено более общее основание осторожности: доступ к полю зависит от поддерживаемых patterns, а способ записи не становится универсальным от одного использования UIA.

## Выводы для архитектуры LShift

1. **Определяющий выбор — путь ввода.** C#/C/C++ сами по себе не объясняют статтеры. Важно, требуется ли возврат нашего кода для продолжения доставки клавиши, что он делает и может ли ждать. Microsoft рекомендует Raw Input для асинхронного наблюдения вместо LL hook во многих подобных случаях. [LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc).
2. **Детектор жеста и работа с текстом должны быть независимы.** В обработке событий — только короткий FSM физического левого Shift и состояние отмены. В worker — проверка фокуса, ограниченное чтение, конвертация и редактирование. Очередь ограничивается; устаревшая команда отбрасывается.
3. **История клавиш не равна содержимому поля.** Она расходится с редактором при вставке, автокоррекции, перемещении курсора, смене фокуса, пользовательских контролах и перехваченных сочетаниях. Для LShift предпочтительно получать актуальный текст по жесту, не поддерживать глобальную историю текста.
4. **Наличие HWND, IBeam или TextPattern не является достаточным разрешением на исправление.** Нужны проверяемые capabilities редактирования, password/read-only ограничения, принадлежность диапазона активному полю, неизменность контекста. При неопределённости команда должна остановиться до изменения данных.
5. **Смена языка требует проверки фактического результата.** Синтетический Alt+Shift зависит от настроек системы. Постановка `WM_INPUTLANGCHANGEREQUEST` также не доказывает, что редактор принял раскладку. Текст и язык не образуют общую транзакцию.
6. **Clipboard не выбирается как незаметный fallback.** Исследованные варианты показывают потерю форматов, обработку прежнего содержимого и гонки с другими приложениями. Даже snapshot с marker/sequence уменьшает лишь часть рисков.
7. **Работа вне синхронного callback не равна доказанному отсутствию статтеров.** Остаются CPU/пробуждения и стоимость вызовов в целевом приложении. Финальное решение требует измерений времени кадров и поведения ввода.

Требование «любой текстовый input» сохраняется как цель. Внешняя утилита не может гарантированно исправлять текст в контроле, который не предоставляет доступ к тексту и редактированию. Нельзя скрыто заменить это требование списком из Discord и Telegram; они нужны как реальные примеры, а поддержка должна определяться возможностями поля. Недоступное поле остаётся открытым вопросом совместимости, а не согласованным исключением продукта.

## Следующая работа

Рекомендуется исследовательский прототип с двумя независимо проверяемыми частями:

- **Наблюдатель:** C++20/Win32, Raw Input, физический левый Shift, отмена при удерживаемой W/модификаторах/постороннем вводе/смене окна, без чтения текста и глобального mouse hook.
- **Текстовый доступ:** отдельный COM MTA worker, сначала только определение поля и чтение диапазона. Сравнить стандартные Edit/RichEdit, браузерные input/textarea/contenteditable и реальные поля Discord/Telegram; проверить пароль, read-only, неподдерживаемый custom control и зависший провайдер. Ни один запрос UI Automation не выполняется из обработчика клавиатурных событий.

Для редактирования сравнить адресный API стандартного контрола и UI Automation с контролируемым вводом. Проверить реальный текст, выделение, undo, курсор, форматирование, отказ раскладки и гонки фокуса. Массовый `ValuePattern.SetValue` всего поля ради одного слова нельзя объявить полноценной заменой диапазона. TextPattern не имеет универсальной команды записи диапазона. [Microsoft TextPattern](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-about-text-and-textrange-patterns).

Анализ существующих решений не снимает оставшиеся компромиссы: приложение видит оба Shift, может выполнить собственную горячую клавишу; внепроцессный ввод через SendInput не атомарен со сменой фокуса; UIA зависит от качества провайдера. Условие завершения следующего этапа — наблюдаемые данные о доступности полей и стоимости обработки, прежде чем выбирать универсальный путь записи.
